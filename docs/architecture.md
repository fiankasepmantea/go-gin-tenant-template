# Architecture

## Layout

Follows the official Go guide [Organizing a Go module](https://go.dev/doc/modules/layout) for a *server project*:
all logic in `internal/`, binaries in `cmd/`, non-Go files (deployment, scripts) next to both.

- `cmd/<binary>/main.go` is thin: load config, wire dependencies, run. No business logic.
- `internal/` cannot be imported by other modules, so internal APIs can be refactored freely.
- **No `pkg/`**: no code is intentionally exported. If a part is useful to other projects, split it into its own module.
- Avoid package names such as `utils`, `common`, `helpers`.
- Organize by **feature** (`modules/user/`), not by kind (`controllers/`, `models/`).

## Layers and dependency direction

```
transport (rest/grpc)  ->  modules (handler -> service -> repository)  ->  platform / core
```

- `handler` only translates HTTP/gRPC <-> service (bind, validation, error mapping).
- `service` contains business rules and depends on the repository **interface**.
- `repository` accesses the database and returns domain entities.
- `platform/*` packages must not import `modules/*`.
- Between modules: go through interfaces, do not import another module's internal packages.

## Differences from the CI4 template (Dhiva)

In PHP, a child *overrides* a parent method and the parent calls the child's version. Go has no such inheritance
(embedding is not polymorphism). The equivalents:

| CI4 | Go |
|---|---|
| `BaseModelSql` + `$providers` | `core.BaseRepository[T]` + module registration |
| `insert()` override in the child | hook via interface (`BeforeCreate`, `Scope`) |
| `DhivaRoutes::Route(...)` | `module.RegisterRoutes(group)` generated by the generator |
| `endpoint` table (whitelist) | Gin routes synced to the `endpoint` table, checked by RBAC middleware |

## Generic repository and tenant transactions

- `core.Repository[T, *T]` provides CRUD, pagination, and an automatic `tenant_id` filter for models that have `SetTenantID`. Models without that method are treated as global tables.
- `database.InTenantTx(ctx, db, level, fn)` opens a transaction and sets `app.current_tenant`/`app.current_level` for RLS. The auth middleware calls it with the tenant and level from the token.
- Two isolation layers are applied together: a filter in the application and RLS in the database. `test/integration` proves that each works on its own.
